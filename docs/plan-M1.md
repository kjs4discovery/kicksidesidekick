# Milestone M1 — full instructions

Copied from the planning chat's build plan (vault), 2026-11-04 23:05. The user starts M1 with a short prompt that points here.

## Part M1a — song format v1, compiler, starter songs

```text
Follow CLAUDE.md and docs/HANDOFF.md. Milestone M1a = build-plan steps 1.1-1.3 in
one go. No hardware.

1. Song format v1 → docs/song-format.md. Start from the vault's Song Format Draft
   (the user will paste it, or use songs/amazing-grace/song.yaml as the reference)
   and decisions D009/D014: a song is a folder with song.yaml (metadata, rights,
   key, time signature, tempo, pickup_beats, form, layers, chord chart with "." beat
   holds, "N.C.", ending) and song.mid (tracks drums, bass, harmony, melody,
   variants :1..:3). Define the compiled binary format too (header, magic, version,
   checksum, bounds for every count/offset, chord track with display symbol and
   keyboard voicing per difficulty, bar/beat map so the device can show "this bar +
   next 3 bars"). Keep v1 small; list what's deferred.
2. tools/fm1song (Python, core logic separate from the CLI so a website can reuse
   it later): validate, compile, info, dump --json. Clear errors with bar:beat.
   Deterministic output. pytest tests incl. malformed files and a fuzz test.
3. Starter songs, at least 3, target 5, all public domain or simple forms, our own
   arrangements, generated by a reproducible script (note in songs/README.md that
   they're generated: relevant to D004):
     - amazing-grace (exists: update to v1, keep the music)
     - 12-bar blues in C, 4/4 swing/shuffle
     - When the Saints Go Marching In, F, 4/4, 3-beat pickup
     - (if time) I-vi-IV-V in G, straight 8ths; Scarborough Fair, D dorian, 3/4
   Each: drums, bass, harmony, melody, with variants :1 and :2 for bass, drums and
   harmony (harmony level 1 = root-position triads held; level 2 = inversions /
   rhythm), a chart, sections. Render audio previews like amazing-grace's.
4. Write a short summary for review in LOG and STOP: the planning chat reviews the
   format before M1b builds the device side on it.
```

## Part M1b — on-device player, song select, hardware checkpoint (prepare only)

```text
Follow CLAUDE.md and docs/HANDOFF.md. Milestone M1b = steps 1.4-1.5 plus a
hardware checkpoint. Replaces the step 0.7 prototype's MIDI-file player.

1. Device-side parser for the compiled format (step 1.4): standalone C, no hardware
   dependencies, bounds-checks everything, never crashes; fuzzed on the laptop
   under ASan/UBSan for at least 10 minutes.
2. Songs on the device: for this milestone, bundle the compiled songs into the
   build (resource region or flash data area, your choice, explain it). `fm1song
   send` comes later (step 1.7). The parser checks each song at first use, not
   during boot.
3. Player (step 1.5): our own scheduler driving EAS from the compiled events
   (D017: no copied GPL code). Four layers; mute any layer at any time (no hanging
   notes); difficulty per layer (variants); tempo 50-120 % during playback without
   drift; count-in (1 bar, aware of pickups) on/off; loop whole song or current
   section (handle pickups at loop points).
4. Screens (simple; full design comes in step 1.6):
   - Song select (list, title, key, tempo).
   - Play screen: big current chord, a **bar strip** = this bar + next 3 bars with
     chord names in boxes, current beat moving through the first box, and a beat
     countdown in the last bar before a change (user feedback: "NEXT" showed a
     change a bar too early when a chord lasted two bars). Layer mute states,
     tempo, loop on/off. Keep CPU/voices as a small debug line.
   - Propose a control map in docs/controls.md (keep REC, OCT-, OCT+ free for rescue).
5. Emulator tests for every song (headless): plays to the end, mutes, tempo change,
   loop, chord display never late, flash IDs 856014 / b36014 / unknown.
6. Prepare the hardware install (same rules and pre-flight as step 0.7; restore
   paths unchanged), write docs/step-M1-install.md, and STOP for review.
```
